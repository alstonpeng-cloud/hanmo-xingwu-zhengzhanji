# 设计评审（design-review）

来源：改写自 Donchitos/Claude-Code-Game-Studios v1.2.0 的 `design-review`（MIT，见 `.trae/skills/LICENSE-claude-code-game-studios.txt`）。已移除 Agent 子代理编排、AskUserQuestion、review-receipts/gdd-structure-check 脚本与 GDD 目录契约；评审维度与结论枚举保留。

## 用途

在实现之前，对一份设计文档做四维评审：**完整性 / 内部一致性 / 可实现性 / 与既有设计一致**。

**只读**。除第 5 步获批准的记录追加外，不改任何文件。

参数：`design-review [文档路径] [--review full|lean|solo]`，默认 `lean`。
- `full`：四维全查 + 三个视角自检（战斗/经济/QA），最慢
- `lean`：四维全查，单会话完成（默认）
- `solo`：只查完整性与一致性，跳过可实现性细查

---

## 第 1 步：确认是否重复评审

如果 `docs/design/reviews/[文档名]-review-log.md` 存在，读最后一条记录：
- 文档**未改动**且上次结论为 APPROVED → 直接告知："该文档与 [日期] 评审时一致，上次结论 APPROVED。" 并问是否复用结论
- 文档**未改动**且上次结论是"需修改" → 说明"文档没变，上次问题仍在，下一步是改文档而不是重评审"，可展示上次问题清单
- 文档**已改动**或没有记录 → 走完整评审

**不要做"只复审改动的部分"**：跳读会漏掉全文级问题，且省不了多少成本。

---

## 第 2 步：读文档与上下文

1. 完整读目标文档（大文件按标题 Grep 定位后分段读）。
2. 读 `docs/troop-balance.md` 的相关章节作为设计基线；若目标文档就是它，则跳过重复读。
3. 读 `docs/playtest-report.md` 中与该系统相关的实测结论。
4. 若文档提到依赖的系统/数值，去 `src/data/config.js` 核对**实际值**；文档写的和代码不一致，本身就是一条问题。

---

## 第 3 步：完整性检查

按本项目的设计文档习惯（不是通用 GDD 模板）逐项判定 REQUIRED / ADVISORY：

| 检查项 | 要求 | 级别 |
|---|---|---|
| 目的/概述（一段话说清这个系统解决什么） | 有 | REQUIRED |
| 明确规则（不含"适当""合理"这类模糊词） | 有 | REQUIRED |
| 数值公式与变量定义（伤害、成长、掉落、经济都要有） | 有 | REQUIRED（凡定义数值规则） |
| 边界情况（上限、下限、满级、空编队、零资源） | 有 | REQUIRED |
| 依赖关系（影响哪些系统/数据文件） | 有 | REQUIRED |
| 可调参数清单（参数名、默认值、范围） | 有 | ADVISORY |
| 验收标准（可独立测试，不是"手感好"） | 有 | REQUIRED |

空标题（只有占位符）视为缺失。附录/历史调整记录不参与完整性判定。

---

## 第 4 步：一致性与可实现性

**内部一致性**
- 公式代进边界值是否产出负数/除零/无意义结果
- 边界情况是否与主规则矛盾
- 依赖是否双向（对方文档/代码是否也知道这个改动）

**可实现性**
- 规则是否精确到不需要猜
- 是否有"这里之后再细化"的空档
- 性能影响是否考虑（尤其 4 MB 包体与 Canvas 渲染：新增贴图/特效是否会顶爆包体或掉帧）
- 每条验收标准是否可独立测试：`感觉平衡`、`正常工作`、`性能良好` 都不算，逐条引用并给出可测改写

**与既有设计一致**
- 是否与现有机制冲突（克制环、合成、经济产出）
- 是否产生意外联动（例如新增 buff 与战法倍率叠加）
- 是否符合项目既定风格与取舍（低包体、单文件、无引擎）

**跨文档数值核对**：把文档里出现的所有数值关键词（兵种名、参数名）在目标文档全文搜一遍；文档在不同章节给出同一参数的不同值时，逐条列出：行号、本文档值、`src/data/config.js` 实际值。

---

## 第 5 步：输出

```
## Design Review: [文档标题]
复评审：[是 — 上次结论 X / 否 — 首次]
评审模式：[full / lean / solo]

### 完整性：[X/N 项必备项已具备]
[只列缺失的 REQUIRED 项；ADVISORY 缺口单独标注"建议补"，不算缺失]

### 依赖检查
- ✓ [依赖] — 存在（路径）
- ✗ [依赖] — 不存在（路径）

### 数值核对
[搜了哪些词、命中多少行、每处冲突的行号与两个值；没有可核对对象就写"无可核对数值"]

### 实现前必须修（阻塞项）
1. [问题] — [证据：文件:行]

### 建议修改（不阻塞）
1. [问题]

### 可选项
[低优先级改进]

### 范围信号
- S：单系统、无公式、<3 个依赖
- M：中等复杂、1~2 个公式、3~6 个依赖
- L：跨系统、3+ 公式
- XL：牵动 5+ 依赖或多个核心系统
标注为"粗略范围信号：M（实现前需人工确认）"

### 结论：[APPROVED / NEEDS REVISION / MAJOR REVISION NEEDED / NOT ASSESSED]
```

**`NOT ASSESSED` 的使用**：文档不存在、读不了、所需章节为空，或依赖的文档缺失导致判据无法应用时用它。其余三个结论都是对设计质量的主张，只有真的读了并判断过才能给。**APPROVED 是危险默认值**——找不到输入不能算通过。`NOT ASSESSED` 在汇总时优先于 APPROVED，但低于两个"需修改"结论（已知问题比未知问题更可行动）。

结论规则：任一阻塞项 → NEEDS REVISION；核心规则互斥或无法实现 → MAJOR REVISION NEEDED；仅建议项 → APPROVED。

---

## 第 6 步：后续（用普通文字提问，等回答）

若 NEEDS REVISION / MAJOR REVISION NEEDED：
- `[A] 现在就改` — 逐条处理阻塞项，一次性列完所有需要用户拍板的设计决策再动手
- `[B] 先停，另开一轮改`
- `[C] 接受现状继续`（仅当没有阻塞项时提供）

改完后展示"阻塞项 → 修复内容"对照表，并问是否重新评审。

若 APPROVED，询问是否追加评审记录到 `docs/design/reviews/[文档名]-review-log.md`（格式）：

```markdown
## Review — [YYYY-MM-DD] — 结论：[APPROVED / NEEDS REVISION / MAJOR REVISION NEEDED]
模式：[full/lean/solo] · 范围信号：[S/M/L/XL]
阻塞项：[数量] | 建议项：[数量]
摘要：[2~3 句]
发现：
- [BLOCKING] [章节]: [一句话]
- [RECOMMENDED] [章节]: [一句话]
```

---

## 边界

- 只读评审，不擅自改设计文档（追加评审记录需明确同意）。
- 不评估美术观感、不评估代码风格（那是 code review 的事）。
- 缺少必要输入时给 `NOT ASSESSED`，不硬凑结论。
