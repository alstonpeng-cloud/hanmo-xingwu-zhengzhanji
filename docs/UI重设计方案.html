01 / DIAGNOSIS

现状诊断：问题不在表面

我逐一查看了 30+ 界面与核心绘制层。现有 UI 有统一的基础控件，但缺少「系统」——颜色靠手写 hex 散落在每个文件，没有语义、没有层级、没有状态规范。以下是五个结构性问题：

问题 01 · 色彩

金色被过度使用，失去语义

金色同时承担货币、标题、按钮描边、稀有度与强调，满屏泛金，反而没有真正的视觉焦点；红/绿/蓝都是孤立色值，不构成语义系统。

改法：朱砂=行动/危险，鎏金=货币/尊贵，竹青=收益，靛青=敌方，紫檀=稀有。每色有明确岗位。
问题 02 · 字体

无字号层级，题材感弱

全站单一黑体，字号零散（28/34/22…）无比例关系；汉末题材完全靠 Q 版立绘支撑，文字层面没有任何书卷气。

改法：宋体做标题/大字数字，黑体做正文；建立 8 级模块化字号阶梯，形成清晰层次。
问题 03 · 结构

信息密度失衡，缺少呼吸

首页塞入 15+ 入口，关卡页奖励格密密麻麻；所有区块都是同一种「深灰描边卡」，没有主次，视线无处落脚。

改法：建立 4pt 间距网格 + 三级表面层次，主按钮、主数据用朱砂/鎏金拉开层级，次要信息降噪。
问题 04 · 组件

控件无状态规范

按钮仅 active / disabled 两态，缺 hover、press、loading；没有统一的标签、徽章、Tab、进度条规范，各处重复手写。

改法：定义 12 类基础组件及完整状态；component 收敛到 draw.js，页面只传参数。
问题 05 · 工程

颜色硬编码，无法统一换肤

hex 值散落在 40+ 文件（config、screen、render），改一个主色要动几十处，极易遗漏、产生不一致。

改法：新建 tokens.js 作为唯一色彩/字号来源，扩展 THEME，所有绘制引用 token。
问题 06 · 可访问性

对比度与触控不达标

次要文字 #5f6b7f 在深底上对比度不足 4.5:1；部分按钮热区偏小，数字标签仅靠颜色区分。

改法：文字阶梯全部校准至 AA；状态用「颜色 + 文字/形状」双通道；热区 ≥ 88 逻辑像素。
一句话结论：现有代码质量不错（逻辑与数据分离得很干净），问题集中在「表现层缺乏系统化」。因此这次改造的价值是——用一套 token + 组件层，让未来所有界面自动保持一致，而不是逐屏打补丁。
02 / DIRECTION

设计方向：汉帛 · 朱金

保留 Q 版轻松的内核，把「汉末」从立绘延伸到界面本身——像展开一卷竹简帛书：暖墨为纸，朱砂为印，鎏金为饰。

以墨为纸，
以朱为印，
以金为饰。

从冷蓝灰的工具台，转向带温度的暖墨色阶；把泛用的金色收敛为「货币与尊贵」的专属信号，让朱砂红成为每一次关键行动的视觉锤。标题用宋体承载历史厚重感，正文用黑体保证小屏可读性——题材与实用，各司其职。

暖墨书卷印玺朱砂鎏金点题宋体标题克制装饰语义清晰

设计三原则

  • 一方寸，一重心 —— 每屏只留一个朱砂主按钮，视线有落点
  • 色必有义 —— 颜色先表意，再装饰，绝不混用
  • 字有层级 —— 宋体镇场，黑体叙事，数字用等宽感
  • 留白即呼吸 —— 8pt 网格，宁可少放，不塞满
  • 状态可感 —— 每个可点元素都有完整反馈态

3.5

图标 · 动效 · 可访问性

规范补充

图标 Icon

统一线性风格，2px 描边、圆头端点、24×24 网格。货币用实心金色圆形徽章；功能图标（返回/设置为/音量）用中性色，仅在激活时着朱砂或鎏金。

动效 Motion

缓动统一用 ease-out-quart；界面转入 220ms，按钮按下 90ms，飘字上浮 600ms。尊重系统「减少动态效果」设置，关键时刻（胜利/抽卡）才用强反馈。

可访问性 A11y

正文对比度 ≥ 4.5:1，大字 ≥ 3:1；状态采用「颜色 + 文字/形状」双编码；触控热区 ≥ 88 逻辑像素；数字用等宽感字体便于对齐比较。

工程落地 Engineering

新增 tokens.js 导出色彩/字号/间距常量；扩展 draw.js 的 THEME 与组件函数；各 screen 逐步替换硬编码 hex 为 token 引用，零行为改动。

05 / BEFORE & AFTER

新旧对比

同样的数据、同样的功能，规范之后的变化是「系统性的」而非「装饰性的」。

✕金色满屏泛滥，货币/标题/描边/强调混为一色
✕单一黑体，字号零散无层级，题材感靠立绘独撑
✕所有区块都是同一种深灰描边卡，主次不分
✕颜色硬编码在 40+ 文件，改一处要翻全项目
✕按钮仅两态，缺少按下/加载等反馈
改后 · 汉帛朱金
✓朱砂=行动、鎏金=货币、竹青=收益，色各司其职
✓宋体标题 + 黑体正文 + 8 级字号阶梯
✓三级表面层次 + 8pt 网格，朱砂主按钮聚焦视线
✓tokens.js 单一数据源，换肤/改色一处生效
✓组件含完整状态，交互反馈一致且可访问
06 / ROADMAP

落地路径与改造范围

「先看方案再决定」——若通过，以下是我建议的分阶段实施方式，纯表现层改造，不动任何游戏逻辑与数值。

阶段一

建立设计 Token 基座

新建 src/render/tokens.js，导出色彩、字号、间距、圆角常量；扩展 draw.js 的 THEME 与 setFont，加入宋体展示字体与完整字号阶梯。此阶段界面外观不变，为后续替换做准备。

阶段二

升级公共组件层

在 draw.js 中增强 button / panel / bar / chip 等函数，支持新的状态（press/loading）与语义色参数；新增稀有度描边、宋体大标题等绘制助手。所有页面无需改逻辑即可调用。

阶段三

逐屏替换硬编码色值

按「首页 → 关卡 → 商城 → 战斗 → 结算 → 布阵 → 其余」顺序，把各 screen 内的 #hex 替换为 token 引用，接入新按钮与标题。每完成一屏跑一次冒烟测试，确保零行为回归。

阶段四

视觉走查与可访问性校准

统一截图走查、对比度检测（正文 ≥4.5:1）、触控热区核对；更新备案截图。产出一份「设计规范 + 组件用法」文档，供后续迭代遵循。

维度改造前改造后风险
游戏逻辑 / 数值—完全不动无
涉及文件40+ 文件散落色值集中在 tokens.js + draw.js低
视觉效果冷蓝工具感暖墨书卷气需你确认
414 / 微信小游戏双端共用 draw.js继续共用，无额外适配低
回滚成本—token 集中，可快速切回旧色板低

推荐 · 完整落地

按方案全量实施

按四阶段路径完成 token 基座到逐屏替换，交付全新视觉与规范文档。

渐进 · 先基座

先做阶段一、二

先建设计系统与组件层，外观暂不大变，后续再逐屏切换，风险最低。

调整方向

先改设计方向

保留冷蓝色系但套用本规范结构，或调整朱砂/鎏金配色，我再出新版方案。
