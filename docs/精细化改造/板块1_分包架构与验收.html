本板块不改任何界面视觉，只把「素材放得下、放得好」的地基铺完。

03体积预算（效果优先）

不做有损压缩，按素材原始质量预留；4 MB 主包与 30 MB 总包由构建脚本硬校验，超限直接构建失败。

分区当前实测预留上限内容 / 理由
主包2.32 MB4.00 MB（硬线）代码 + 首屏精灵 + 标题图 + 音效 + 占位循环。首帧零等待。
pkg_audio1.29 MB6 MB主 BGM 1.32 MB；后续可加多首高码率场景曲，不必压到 80 kbps。
pkg_heroes0（待板块 4）12 MB24 张立绘，单张按 400–600 KB 原图估算，留足写实厚涂细节。
pkg_siege0（待板块 4）5 MB器械与兵模高清贴图，避免低分辨率导致兵模糊。
pkg_art0（待板块 4）4 MB边框 / 宝箱 / 光效贴图，参考图里最吃质感的 B 类要素。
合计3.61 MB≈ 24 MB / 30 MB刻意留约 6 MB 冗余，后续加素材不必反复腾挪。
一个取舍说明：分包是按「整包」下载的，包越大单次下载越久。因此没有把 24 张立绘塞进一个 20 MB 的巨型包，而是按系统拆成 4 个、串行下载——声音先到、立绘随后，玩家在首页就能感知到画面逐步变精致，而不是一开始卡在加载条上。

04启动时序与回退

首帧优先渲染，下载在后台静默进行；任何一步失败都有兜底，不影响可玩性。

场景系统行为玩家感知
分包未就绪resolveAsset() 返回 null；音频用 48 KB 占位循环，图片走程序化绘制首屏有声音、有兵模，不等待
下载中onProgressUpdate 写入 packageSnapshot()，供后续板块做进度提示无感，可正常开局
audio 就绪音频层销毁占位轨、同轨重建高音质主曲并续播当前场景音质自然提升，不切断
单次失败自动重试 2 次，间隔递增（0.9 s / 1.8 s）短暂波动后自愈
彻底失败 / 断网标记 failed，资源永久回退主包占位；下次启动会重新尝试游戏完整可玩
本地预览 / 冒烟非微信环境一律视为就绪，路径直通 assets/开发链路零改动

打回修改记录 · 一次真实缺陷

首轮 33 项校验全过，但复核产物目录时发现 wechat/pkg_heroes/heroes/verify_fixture.png 残留—— game.json 只声明 audio，模拟构建留下的旧分包目录却仍在产物里，会被上传流程算进总包。 根因是构建脚本在「清空 wechat/ 被环境拦截 → 覆盖式同步」时没有清理历史 pkg_* 目录。

已修复 ①：构建开始后无条件逐文件清理所有历史 pkg_* 目录（不依赖可能被拦截的递归删除）； 校验脚本新增两条断言——「无未声明的历史分包目录残留」「模拟分包目录已彻底清理」。
已修复 ②：连续复跑时发现「每个新会话首次校验偶发 7 项误判」——根因是校验脚本读的是外部遗留的 wechat/ 状态，读到旧版空映射表会让所有分包断言连锁失败。现改为校验前先自行构建一次、 并把固定毫秒等待全部换成事件驱动等待。连续多次 + 跨会话复跑均为 35 通过 / 0 失败，最终产物只剩 pkg_audio。

07板块 4 的素材约定

提前写清调用方式，避免后面生成了立绘却接不进画面。

// 逻辑路径永远写 assets/ 开头的原始位置，运行时统一解析
import { resolveAsset, ensureSubpackage, onPackageReady } from '../core/subpackage.js';

// 1) 渲染前取真实路径；null = 分包还没到，用程序化建模兜底
const src = resolveAsset('assets/heroes/guan_yu.png');
if (src) platform.loadImage(src, (img) => { ... });

// 2) 进入招募页时按需确保立绘分包已下载
ensureSubpackage('heroes');

// 3) 就绪后重绘当前页，或做一次淡入替换
onPackageReady('heroes', () => refreshCurrentScreen());
约束：分包之间不能互相 require 代码，因此分包里只放图片 / 音频这类纯资源，所有绘制与业务逻辑继续留在主包。这也是本方案把「代码」和「美术材质」彻底分开的原因。
